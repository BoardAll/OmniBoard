# 局域网投屏：源码调查与实施报告

> 范围：为 OmniBoard 增加「局域网 WebRTC 投屏」能力（四位投屏码 = 投屏房间号，复用互动白板实时服务，媒体 P2P）。
> 本文记录**开工前的真实源码调查**、复用点决策与分阶段落地情况；所有路径均来自仓库实读。

## 1. 仓库结构与入口

| 层 | 路径 | 关键事实 |
| --- | --- | --- |
| 桌面端 | `apps/desktop` | Flutter（Windows 主力），Miuix 组件库；`lib/main.dart` → `lib/app.dart`（MultiProvider 装配）→ `lib/routes.dart`（`WbRoutes` + go_router） |
| Web 端 | `apps/web` | Flutter Web；首页 `lib/pages/board_list_page.dart`，编辑页 `lib/pages/board_edit_page.dart`（约 1500 行） |

- `/settings` → 设置页

## 2. 互动白板服务（复用对象）

服务装配：`services/realtime/src/server.ts`

- `createRealtimeApp()` 创建 `express` + `http.Server` + `new Server(...)`；
- `attachBoardNamespace(io, {env, audit, rooms})` 挂载 `/board`；
- 房间存储 `BoardRoomStore`（`src/roomStore.ts`）：参与者、op 环形日志、去重、水位、软锁、checkpoint、host 转移、空房清理；
- 鉴权 `src/token.ts#resolveConnectionIdentity`：HS256 `WB_JWT_SECRET` 验签；非 production 无密钥/无 token 回落 `anon-<random>`；
- 审计 `src/audit.ts`（注入 / JSONL / stderr 三级），入口 `buildAuditEntry`；
- 协议类型集中在 `src/types.ts`；事件 `board:join / joined / joinAck / ops / fetchOps / leave / ping / participants / room:error / session`；
- 测试：`vitest` + `socket.io-client`，公共装配 `tests/helpers.ts`（`startTestServer`、`emitAck`、`waitForEvent`、`signTestToken`）。

房间号现状：白板房间 id 是**业务侧字符串**（`boardId`，如 `board-<timestamp>`），不存在四位数字分配机制；因此投屏码不能复用白板房间号规则，需要**独立的四位码空间**。

### 2.1 复用决策（最高优先级约束）

投屏实现为**同一 realtime 进程、同一端口、同一 Socket.IO 实例上的第二个 namespace `/cast`**，复用：

- 连接鉴权（`resolveConnectionIdentity`）与审计 sink；
- “房间 + 成员 + 定时清理”的既有设计口径（与 `BoardRoomStore` 同构）；
- 既有测试基础设施与运行方式（`npm test` / `tsc --noEmit`）。

**不复用** `BoardRoomStore` 本体（不是给它加 `type` 字段）：其 oplog / 软锁 / checkpoint / host 转移只对白板文档同步有意义，混入会把投屏状态带进白板广播与清理路径。投屏使用独立 `CastRoomStore`（`src/castStore.ts`），与白板房间物理隔离——关投屏房间不可能触达白板房间。

## 3. 投屏房间与信令（本期新增）

| 文件 | 职责 |
| --- | --- |
| `services/realtime/src/castTypes.ts` | `/cast` 事件与载荷类型、常量（四位码正则、TTL、并发上限、宽限期） |
| `services/realtime/src/castStore.ts` | 四位码分配（`0000`–`9999`，字符串保留前导零）、席位、有效期、断线宽限、错误码限流、房间/单路移除回调 |
| `services/realtime/src/cast.ts` | namespace 装配、鉴权中间件、事件处理、SDP/ICE 精确路由、审计 |
| `services/realtime/src/server.ts` | 挂载 `/cast`、暴露 `castRooms`、关闭时 `dispose` |
| `services/realtime/tests/cast.test.ts` | 20 项契约测试（房间生命周期、限流、串线隔离、断线恢复、与 `/board` 隔离） |

关键语义：

- 接收端 `cast:create` → 服务端分配四位码，ack 返回 `receiverToken`，之后才允许显示投屏码；
- 发送端 `cast:join` → 服务端校验格式/存在/接收端在线/容量/限流；`autoAccept` 直接 `cast:accepted`，否则接收端 `cast:decision` 接受/拒绝；
- `cast:offer / cast:answer / cast:ice` 只转发文本；发送端方向由服务端按其 socket 会话回填 `senderId`（忽略客户端伪造），接收端方向必须命中本房间已接受的 `senderId`；
- 换码 `cast:regenerate`：旧码立即失效、已接受席位保留，并迁移 socket.io 房间成员关系（否则接收端会收不到新码请求）；
- 关闭/过期/接收端离线超时 → `cast:roomClosed`；单路离开/被踢 → `cast:peerLeft`；
- 断线恢复：`cast:resume` + `receiverToken`/`senderToken`；JWT 身份下额外校验 `userId`，匿名开发模式以 128-bit token 为凭证；
- 错误码：`InvalidCode / NotFound / RoomFull / ReceiverOffline / TooManyAttempts / AlreadyInRoom / Forbidden / ConnectionsExceedLimit` 等；
- 审计：`cast.roomCreated / cast.join / cast.accept / cast.reject / cast.regenerated / cast.roomClosed / cast.receiverOffline / cast.senderOffline / cast.auth.rejected`，投屏码脱敏为前两位 + `**`。

## 5. 依赖与平台现状

| 能力 | 现状 |
| --- | --- |
| WebRTC | 仓库内**无**既有实现与依赖（`services/sfu` 为空目录；桌面/Web pubspec 均无 webrtc） |
| 信令客户端 | 桌面/Web 现有协同走 C++ 引擎的 Socket.IO 传输（FFI），Dart 侧无可直接复用的通用客户端；Web 另有 `apps/web/lib/services/socketio_js.dart`（JS 桥） |
| 摄像头/屏幕采集 | 桌面端无既有采集能力 |

本期新增依赖（`packages/cast/pubspec.yaml`，已 `flutter pub get` 通过）：

- `flutter_webrtc ^1.6.2`：`RTCPeerConnection` / `RTCVideoRenderer` / `RTCVideoView` / `getUserMedia` / `getDisplayMedia`；Windows 原生屏幕采集可用；Windows 构建需下载预编译 `libwebrtc`（网络依赖，属构建风险点）；
- `socket_io_client ^3.1.6`：纯 Dart，VM + Web 通用，直连 `.../cast` namespace。

平台结论：

- **桌面端（Windows）**：摄像头与屏幕采集均可用，是本期真实投屏闭环的目标平台；
- **Web 端**：`getUserMedia/getDisplayMedia` 要求安全上下文（https / localhost）；局域网 HTTP 页面
  `navigator.mediaDevices` 为 `undefined`，无法采集，只能作为接收端（播放不受此限制）。
  此时点投屏会报 `Unable to getDisplayMedia: Null check operator used on a null value`；
  已加前置检测与中文提示（见 §11.4），部署层提供 HTTPS 方案（`tools/packaging/deploy/README.md`）。
- 移动端目录为空，不在本期范围。

### 7.1 真实 WebRTC 闭环实测（浏览器）

环境：Edge 155 headless（`--use-fake-device-for-media-stream` 提供真实视频轨）、`apps/web` 生产构建 `http://127.0.0.1:8090`、realtime `http://127.0.0.1:8790`（同一进程提供 `/board` 与 `/cast`）。

链路与断言：接收端 `#/board/<id>?cast=1` 自动建房并展示服务端四位码 → 发送端首页「输入投屏码」→ 选摄像头 → 「开始投屏」→ 双方交换真实 SDP/ICE（媒体不经服务端）→ 接收端出现独立视频浮层（`videoWidth > 0`、`readyState=4`、video track `live`）。四路截图可见独立浮层错位堆叠、每路「已连接」与「4/4 路」。

实测暴露并修复的 3 个缺陷（均有回归防护）：

1. **SDP 尾换行缺失导致 `setRemoteDescription` 失败**：发送端 `createOffer()` 返回的 SDP 末行不带换行符，Edge/Chromium 解析远端描述时报 `Failed to parse SessionDescription … Invalid SDP line`（本地 `setLocalDescription` 不受影响，故发送端无感）。定位方式：CDP 注入包装 `RTCPeerConnection.prototype.setRemoteDescription` 抓取入参（4235 字节 / 129 CRLF / 无非法行），再离线重放验证「补尾换行即成功」。修复：`normalizeWbCastSdp` 在 offer/answer 的收发两侧统一补齐 `\r\n`。
2. **接收端状态不随连接更新**：自动接受时服务端不会单独推 `cast:accepted`，接收端 `_status` 恒为 `waiting`，投屏码卡在已有 1 路时仍显示「等待设备输入投屏码…」。修复：以 `cast:room` 快照的 `acceptedCount` 驱动接收端状态，并让状态文案以实际连接数为准。
3. **错误文案不可被读屏/自动化获取**：`WbCastJoinDialog` 的错误行在 Flutter Web 合并语义节点中丢失。修复：错误行改为 `Semantics(liveRegion: true, label: …)` 独立节点，读屏可播报、自动化可断言（超限拒绝用例因此可验证）。

## 8. 投屏房间号与信令协议

### 8.1 四位投屏码

- 服务端 `CastRoomStore` 用 `crypto.randomInt(0, 10000)` 生成，`padStart(4, '0')` 保留前导零，全生命周期按**字符串**处理，客户端只做格式校验（`^\d{4}$`）与展示复原；
- 冲突时重试分配；房间关闭/过期后从活动表移除，旧码不可再建连；
- 码只用于便捷配对：建房 ack 同时返回 `receiverToken`（断线恢复凭证）；发送端加入需服务端校验房间类型、有效期、接收端在线、容量与限流。

### 8.2 `/cast` 事件（节选）

| 方向 | 事件 | 说明 |
| --- | --- | --- |
| C→S | `cast:create` / `cast:resume` | 建房（ack 返回 `code`、`receiverToken`、快照）；断线恢复 |
| C→S | `cast:join` | 发送端加入（code + 设备名 + 媒体源）；ack 含 `senderId`、`senderToken`、是否 `autoAccept` |
| S→C | `cast:request` | 接收端待确认请求（`senderId`、`deviceName`） |
| C→S | `cast:decision` | 接收端接受/拒绝（只接受本房间 `senderId`） |
| S→C | `cast:accepted` / `cast:rejected` | 发送端收到结果 |
| C↔S | `cast:offer` / `cast:answer` / `cast:ice` | SDP/ICE 转发；发送端方向由服务端按 socket 会话回填 `senderId`（忽略客户端伪造），接收端方向必须命中已接受席位 |
| C→S | `cast:update` | 调整 `maxSenders` / `autoAccept`（低于当前连接数返回 `ConnectionsExceedLimit`，不静默断开） |
| C→S | `cast:regenerate` | 换码：旧码立即失效、已接受席位保留、socket.io 房间成员同步迁移 |
| C→S | `cast:leave` / `cast:close` | 单路离开（含 `kicked`）/ 关闭房间 |
| S→C | `cast:peerLeft` / `cast:roomClosed` | 单路断开 / 房间关闭（含码失效原因） |
| S→C | `cast:room` | 房间快照（连接数、上限、状态） |
| C→S | `cast:heartbeat` | 心跳（接收端 45s；宽限：接收端 30s、发送端 15s） |
| S→C | `cast:error` | 统一错误（`InvalidCode / NotFound / RoomFull / ReceiverOffline / TooManyAttempts / AlreadyInRoom / Forbidden / ConnectionsExceedLimit` 等） |

`/board` 事件与载荷语义不变；投屏事件只挂在 `/cast` 上，不进入白板的 oplog / 元素同步 / 撤销重做路径。

## 10. WebRTC 连接与资源释放

1. 接收端 `startReceiver()`：`/cast` 建房成功并拿到四位码后才 `role=receiver`、显示投屏码；
2. 发送端 `join()`：加入房间（autoAccept 或接收端确认）→ 采集（`getDisplayMedia` / `getUserMedia`）→ `createPeerConnection` → `addTrack` → `createOffer` → `cast:offer`；
3. 接收端按 `senderId` 建立独立 `WbCastPeer`（每路一个 PeerConnection），`setRemoteDescription` → `createAnswer` → `cast:answer`；SDP 在收发两侧先经 `normalizeWbCastSdp` 补齐尾换行（Edge/Chromium 对末行无换行的远端描述报 `Invalid SDP line`）；
4. ICE 双向经 `cast:ice` 转发；先到的 candidate 进入缓冲，远端描述设置后 flush；
5. 接收端 `onTrack` → `RTCVideoRenderer` → `WbCastVideoFeed` → 对应 `senderId` 的视频浮层；
6. 断开/被踢/轨道结束/页面退出：`endSession()`（幂等）→ 逐路 `disconnectSender` / `leaveAsSender` → `close()` PeerConnection、停止本地轨道、`renderer.dispose()`、移除监听、`signaling.disconnect()`；
7. 媒体不经过信令服务：`/cast` 只转发 SDP/ICE 文本，不接触 RTP。

## 11. 已知问题与未验证平台限制

1. **Windows 构建（已解决）**：无开发者模式时构建脚本自动用 NTFS junction 回退插件 symlink；`flutter_webrtc` UTF-8 源码触发的 MSVC C4819/C2220 已通过在 `APPLY_STANDARD_SETTINGS` 中增加 `/utf-8` 修复；`build_cpp` / `build_flutter` / `build_wasm` 在 PowerShell 5.1 下把原生命令 stderr 误判为失败的问题已改为仅按 `$LASTEXITCODE` 判定。`build_all.ps1` 五步全绿（WASM 因未装 EMSDK 优雅跳过）。
2. **真实设备闭环的覆盖边界**：本轮在浏览器（Edge 155 + 真实视频轨，使用 Chromium 假摄像头设备）完成了单路 / 四路 / 超限 / 断开 / 清理的真实 SDP-ICE 闭环；桌面端 Release 已构建成功并完成启动冒烟（首页「白板 / 局域网投屏」入口正常），但**尚未在第二台物理设备、真实摄像头/屏幕源以及桌面↔桌面 / 桌面↔浏览器之间复测**。
3. **跨设备兼容性**：验证了 Chromium 系浏览器互通；Safari/Firefox、Android/iOS、桌面原生 libwebrtc 的互通未验证；屏幕采集仅验证到接口层（headless 下 `getDisplayMedia` 被策略阻断，探针显式改用摄像头）。
4. **Web 发送端（已加兜底 + 部署层 HTTPS 方案）**：`getUserMedia/getDisplayMedia` 要求安全上下文
   （HTTPS 或 localhost）；局域网 HTTP 页面只能作为接收端（播放远端流不受采集限制），
   PC 浏览器点投屏会报 `Unable to getDisplayMedia: Null check operator used on a null value`
   （已用真实浏览器取证：`http://<LAN IP>/` 下 `isSecureContext=false`、`mediaDevices` 为 `undefined`）。
   - 应用层：`packages/cast/lib/src/cast_capture_support*.dart`（条件导入）在 `_capture` 前检测，
     非安全上下文 / 无 `mediaDevices` / 不支持 `getDisplayMedia` 时返回中文提示；Web 端投屏入口
     （`board_edit_page._openCastJoin`）也会提前拦截并 snackbar 提示，不再抛底层空断言；
   - 部署层：`pack_server_deploy.ps1 -Scheme https` 注入 `https://<域名>`（443 同源），
     `install.sh --tls-domain` 渲染 nginx 443 + `/socket.io/` 反代模板
     （`templates/whiteboard-web-tls.conf`），详见 `tools/packaging/deploy/README.md`；
   - **手机浏览器即使 HTTPS 也普遍不支持 `getDisplayMedia`**（Android Chrome / iOS Safari），
     只能作为观看端，或改用摄像头（`getUserMedia`）。
5. **NAT/防火墙**：本期仅验证/设计为局域网直连（主机候选），未配置 STUN/TURN，跨网段或严格防火墙环境可能无法建连。
6. **其他桌面平台**：macOS/Linux 有 `flutter_webrtc` 支持但本期未构建验证；移动端目录为空，不在范围。
7. **浮层布局不持久化**：视频浮层位置/大小仅当前会话内独立管理，不写入白板文档。

## 12. 关键结论

- 四位投屏码直接作为投屏房间号，独立于白板 `boardId` 空间；
- 投屏信令复用 realtime 服务的连接鉴权、审计与运行方式，仅新增 `/cast` namespace 与 `CastRoomStore`；
- `whiteboard` 与 `cast` 房间物理隔离：关投屏房间不影响任何白板房间；`cast.test.ts` 含专项隔离断言；
- 白板只负责投屏 UI 与浮层，媒体由 WebRTC P2P 传输，投屏状态不进入白板文档模型；
- 原有白板客户端协议未改动，新增事件不覆盖旧事件；
- 真实闭环（浏览器）已验证：四位码配对 → 真实 SDP/ICE → 接收端独立视频浮层（单路与 4 路）、超限拒绝、单路断开互不影响、退出后资源全部释放；桌面端 Release 已构建并启动，真实跨设备投屏仍待第二台物理设备复测。
