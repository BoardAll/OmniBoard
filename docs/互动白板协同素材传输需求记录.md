# 互动白板协同素材（图片）跨端传输需求记录

- 状态：需求登记（本轮不实现；M1 保持现状；M2 决策不纳入（聚焦交互体验），保持待排期）
- 提出日期：2026-09-30
- 关联设计：《互动白板实时协同设计文档》§6 消息契约；《Web 端方案设计 Flutter Web + WASM》
- 关联模块：04-core-domain（元素 payload / 文档导入）、11-app-desktop（图片插入 / 渲染 / 保存）、13-svc-api（素材端点，对象存储为预留方向）、03-core-render（图片解码缓存）

## 1. 背景与现状

图片元素载荷是**本地文件路径引用**：`{path, naturalWidth, naturalHeight}`。

| 环节 | 现状实现 | 跨机表现 |
|---|---|---|
| 插入 | `WindowsWindowPlugin().openImageFile()` 取本地路径，写入元素 payload | — |
| 渲染 | `WbCanvasImageCache` 对 `File(path).readAsBytes()` 解码；失败静默占位 | 目标机器无该文件 → 占位图 |
| 保存 | `.wbd` 的 `encodePayload` 对 image 分支原样保留 Map | 同机可复现 |
| 协同 | 落定提交生成 op `el:{id}:data`，value = `encodeElement`（仅含 path 字符串） | 远端从**自己的磁盘**读同路径 → 跨机必然失败 |
| 服务端 | 无素材上传端点；对象存储为 Wave 4 预留 | — |

结论：同机双开（共享磁盘）可用，**跨机图片不可见**；Web 端无图片能力。

## 2. 需求描述

1. 同一互动白板房间内，任一成员插入的图片应能在**其他成员端可见**（跨机、无需人工拷贝文件）；
2. 后加入成员应能看到此前插入的图片（依赖 late-join 历史回放）；
3. 图片像素数据以**素材**形式经协作服务端存取，不随每次 op 广播重复携带大体积数据；
4. 本地模式（未加入房间）维持现有本地路径直读，零改动、零依赖。

## 3. 方案对比

### 方案 A：base64 内嵌进 op

- 优点：无服务端改动，单 op 自包含；
- 缺点：单次 op 体积可达 MB 级（超过 Socket.IO / 服务端载荷上限风险）；每次都进 oplog 与广播；内存与带宽放大严重。
- 结论：**不采纳**。

### 方案 B：素材上传 + URL 引用（推荐）

- 图片插入时上传素材（一次），op 中 value 携带 `assetUrl`（+ 宽高 / 摘要）；
- 渲染层按 URL 拉取并缓存（LRU + 磁盘缓存可选）；
- 优点：op 保持小体积；素材可 CDN 化 / 去重（按内容哈希）；与 .wbd 导出解耦；
- 缺点：需新增素材端点与存储，离线协同需素材缓存策略。

## 4. 采纳方案（B）的改动面（排期时细化）

| 层 | 改动点 | 说明 |
|---|---|---|
| 服务端 | 新增素材上传 / 下载端点（13-svc-api），对象存储 / 本地目录兜底 | 大小上限、类型白名单、鉴权与房间归属 |
| 元素载荷 | image payload 增补 `assetUrl`（保留 `path` 兼容本地） | 契约向后兼容，旧文档不受影响 |
| 桌面端 | 插入时将文件上传素材服务，payload 写 `assetUrl`；渲染优先 URL 拉取（缓存），仅本地模式回落 `path` | `WbCanvasImageCache` 增加网络解码分支 |
| 协同 | 无需新 op 类型：素材引用随 `el:{id}:data` 同步 | late-join 回放即可覆盖历史图片 |
| .wbd | 导出两种策略：内嵌素材（自包含）/ 仅引用（轻量） | 后续设计确认 |

## 5. 验收场景

1. 双机同房：A 插入图片 → B 端画布出现同一图片（跨机）；
2. 先后入房：B 后加入 → 收到历史 op 后图片可见；
3. 断线重连后素材仍可拉取；素材被拒（超限 / 类型不符）时有明确提示且不破坏 op；
4. 本地模式无网络依赖，行为与现状一致。

## 6. 边界与非目标

- 本轮（M1）不实现任何上述改动；仅登记需求与方案结论；
- Web 端图片能力另行排期（Web 无图片插入实现）；
- 离线场景下素材缓存过期策略（LRU / 大小上限）在详细设计阶段确认。
